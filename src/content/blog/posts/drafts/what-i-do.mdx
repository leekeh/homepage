Bonus: How do websites actually work?  
As I come from a family of teachers, I love explaining these technical things to anyone interested, with or without a technical background. Maybe one day I will find the time to write an elaborate course. But for now, here is a very quick summary of it, in case you are interested.  
Let's follow the journey of a website. What happens when you open a website on your phone or computer? The environment you access a website is called a browser, this is something like Google Chrome, Safari, Microsoft Edge, etc. Well, you first start by accessing a url, such as "[https://www.google.com](https://www.google.com/?authuser=0)". We want to find the server that has the content for this URL. However, servers are not registered under a URL, but instead they are identified with IP addresses. To get the IP address, your browser will contact a DNS (Domain Name System) server. Think of DNS as the internet's phone book - it converts human-readable URLs like "[google.com](http://google.com/)" into IP addresses that computers can understand, like "142.250.190.78".  
Once your browser has the IP address, it sends a request to that server asking for the webpage. This request uses a protocol called HTTP (Hypertext Transfer Protocol) or its secure version, HTTPS. The server then responds by sending back the requested files - typically HTML (the structure), CSS (the styling), and JavaScript (the interactive elements).  
Your browser then goes to work interpreting these files. It processes the HTML to create the basic structure, applies the CSS to make everything look right, and runs the JavaScript to add any interactive features. This whole process is called "rendering" the webpage.  
Web developers work to write the HTML, CSS and JavaScript code. They might use different strategies in order to combine this code in an intelligent way. This is all to build up the "frontend" of a website, which is the part that the user sees. Frontend is all about how the user views and interacts with the page. For example, I might write some code to determine what happens when a button is clicked. That could be something like "change the background color", "navigate to a different page" or "request information from the server". That last one brings me to the "backend". In many cases, the backend of a website is a separate concern, written by separate developers in separate codebases. Backends are also hosted on a server, but instead of delivering HTML, CSS and Javascript, they deliver information. For example, from my frontend code I can ask a server "give me the post of user x", and the server will verify the request, access the database to get the requested information, and return it in a schematic way. That can look something like this:

```
{
aa: bbb
}

```

Now, we can use this information in the frontend by using JavaScript.

There is far more complexity to this. There are different ways to mix frontend and backend code, there are a lot of security concerns, there are optimizations, caching so that the server does not need to always look up the same information, and so on. But in the essence, it all boils down to this.

At work, I am primarily a frontend developer, although I have played around with backend when the opportunity was there. In my personal projects, I usually handle all parts of an application, which can be challenging but also very fulfilling :)
